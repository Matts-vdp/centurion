# Centurion

Centurion is a local manager for Claude agents, replacing a terminal "herder". The user runs **chats** in a central project (the managing folder, where the manager is started); a chat becomes an **orchestrator** when the user runs the `/orchestrate` skill. They start **expert** agents in other repositories to research or implement things, collect the results, and plan features that span several repos. The user wants a modern, visually pleasing UI instead of a TUI. The usual flow: the user explains a problem to an orchestrator, it proposes rounds of parallel **tracks** (experts in other repos, an expert in the central folder, subagents), the user approves or adjusts them in the chat, and the orchestrator collects the results.

**Status:** the backend and the UI v1 (`docs/ui-v1-plan.md`, layout from `docs/ui-research.md`) are done and tested end to end on Windows. The v1 look is being replaced by the design in **`docs/ui-design.md`**, which also adds model and effort switching, track plans and question sets; its implementation plan (last section) lists the steps and their status. Archiving chats, split view and permission prompts (`docs/next-plan.md`) are done, and so are experts from the UI, subagent lines, fork and rewind (`docs/fork-plan.md`). Skill autocomplete, the cache countdown and image input (`docs/features-plan.md`) are done, and so are `@` file mentions in the composer (Claude Code expands them, also through the SDK), prompt history and "Open folder in VS Code", and so are desktop alerts (`ui/src/desktopNotify.ts`), and so are the Files panel (`docs/files-plan.md`), git in that panel (`docs/git-plan.md`), keep-warm (the cache tag's popover, `src/keepwarm.ts`), and visuals (`show_visual` markup and Mermaid diagrams, `docs/visuals-research.md`, with a second round of elements for planning and investigating; clicking a card to ask about it comes later). Next: the *soon* items in `docs/ui-research.md`. Later: dev container support (`docs/add-devcontainer-support.md`), repo names instead of absolute paths, configurable notifications, editing files, and a link to the user's own agentic dev system (running, blocked and queued tasks).

Scheduled tasks (`docs/schedule-plan.md`) are implemented: the scheduler, API, agent tools, sidebar group, task page, form and transcript proposal block. They persist in state version 2. The scheduler uses local-time cron through `croner`, with a 15-minute minimum, catch-up policy and a per-task permission policy.

## Layout

- `src/agent.ts`: `AgentRuntime`, one long-lived Agent SDK `query()` per agent (streaming input). Handles the per-agent queue, turn tracking, interrupt and stop, context usage, and closing idle processes.
- `src/manager.ts`: agent registry (a tree: `parentId`), SDK options per agent, routing notifications, restoring state on startup.
- `src/tools.ts`: in-process MCP server `centurion` (the manager tools, `mcp__centurion__*`), given to orchestrators only: `create_expert`, `message_expert`, `get_expert_output`, `list_experts`, `stop_expert`, `propose_tracks`, `ask_user`.
- `src/display.ts`: in-process MCP server `display`, given to every agent: `show_visual`. Its description is the agent's whole guide to the markup. It also checks that linked files, `Code` files and images exist, and compares `Code` excerpts with their file. `src/visual.ts`: the markup parser (Row / Column / Card, Tree / Timeline / Item, More, Code, Bars, Image; limits, icon list, error messages), shared with the UI.
- The `centurion` MCP server also offers `schedule_task` (proposal only), `list_scheduled_tasks` and `pause_scheduled_task`. Activation, Run now and deletion are UI or API actions.
- `src/decisions.ts`: helpers for track plans and question sets (validation, the messages Start and Send turn into). The state lives in `Manager` (`plans`, `questionSets`) and in the state file.
- `src/keepwarm.ts`: `KeepWarm`, the keep-warm scheduler: plans each agent's next ping from its record (`keepWarm`, `cache`, `lastActivityAt`, its experts' state) and runs pings as throw-away forks of the session.
- `src/cron.ts` parses and previews local-time schedules; `src/schedule.ts` decides due, missed and waiting runs and enforces the concurrency limit. `Manager` stores scheduled tasks and links their runs to agent turns. `scripts/test-schedule.mjs` covers cron, catch-up, concurrency and state migration.
- `src/files.ts`: read-only folder listings and file reads for the Files panel. Paths are relative to one of the agent's roots (its folder, then its orchestrator's) and must resolve inside it, links included (`src/confine.ts`: `resolveInside`, `FileError`). `src/git.ts`: git reads (`docs/git-plan.md`): status with staged, unstaged, conflicts, the operation in progress and changes outside the folder, diffs per side, log, commit details and branches. `src/gitwrite.ts`: queued writes (stage, unstage, discard, partial patches, commit, undo commit, remote and branch operations), error mapping, and `gitEvents` for the `git` SSE event. `src/gitconflict.ts`: conflict versions from index stages and inline blocks. Git runs as `git` itself; no git or not a repo means no git fields.
- `src/server.ts`: HTTP API (including `/api/models`, `/api/agents/:id/commands`, `POST /api/agents/:id/model`, `.../experts`, `.../fork`, `.../rewind`, `GET .../subagents/:toolUseId`, `GET .../files/*`, and the git status, diff, side-text, log, commit, branches, rebase-safety, conflict and merge-message reads; stage, unstage, discard, apply, commit, undo, remote, branch, operation and conflict writes under `.../git/*`), server-sent events (`snapshot`, `agent`, `delivered`, `message`, `plan`, `questions`, `permission`, `git`) and the token check. The `git` event carries `{ repo, agentIds }` after a git write. Routes are a table (`routes`: method, path pattern, summary, body, result, handler) that the server dispatches from; `describeRoutes()` and `SSE_EVENTS` are their docs. `src/config.ts`: config loading; the file's fields are a zod schema (`configSchema`, a description and default per field, unknown fields refused) and `describeConfig()` documents them. `src/check-docs.ts` (`npm run check:docs`) fails when a route or config field has no docs. `src/state.ts`: the JSON state file.
- `ui/`: the web UI (Vite + React + TypeScript, plain CSS with theme variables in `ui/src/styles.css`). `api.ts` (token, fetch, commands), `store.ts` (SSE-fed agent store, per-browser view state in `localStorage`), `timeline.ts` (history + live events → transcript items; sender derived from the prompt prefix), `blocks.ts` (transcript items → turns, work logs, delegations, footers), `status.ts` (an agent's one state and its status line), `models.ts` (the models list, model labels, what an agent runs on), `tools.ts` (tool summaries), `layout.ts` (the one or two panes of the main area, per browser), `tabStatus.ts` (the tab title's Needs you count and the favicon's state dot), `desktopNotify.ts` (desktop alerts: per-browser settings, `AlertWatcher` turning store states into alerts, `showAlert`; kept apart for a later service worker) with `AlertsMenu` (the sidebar's bell), `promptHistory.ts` (sent prompts per browser for Up / Down in the composer: the agent's own first, then other agents'), `fileStore.ts` (Files and git API, per-pane panel state, commit drafts, transcript link events), components `App`, `Sidebar`, `Switcher`, `AgentView`, `Header`, `ModelPicker`, `CacheTag` (the cache countdown and its keep-warm popover), `Composer`, `Transcript`, `Delegation`, `Plan`, `Questions`, `Mark`, `Files` (the Files panel, tree and viewer), `DiffView` (the viewer's diffs: unified or split, word highlights, more context, hunk and line staging, moving between hunks; parsing and the word diff in `diffModel.ts`), `Changes` (the panel's git changes: groups, row actions, commit box, result line), `BranchPopover` (branch picker and actions), `ConflictViewer` (inline resolution), `ThreePaneResolver` (aligned three-column resolution, with region matching in `resolverModel.ts`), `Log` (commit graph, details and first-parent file diffs), `Visual` (show_visual blocks) and `Mermaid` (mermaid code blocks, loaded on first use); `highlight.ts` (highlight.js languages, shared by the file viewer and visual `Code`). Permission requests render in `Transcript.tsx` (`PermissionView`). `npm run build` writes `dist/ui`, which `src/server.ts` serves at `/`.
- `prompts/expert.md` and `prompts/orchestrator.md`: the packaged prompts, appended to experts' and chats' system prompt (the chat one only asks for visuals when explaining things) (`{{placeholders}}`, listed in `PROMPT_PLACEHOLDERS` in `src/manager.ts`, are filled in per agent). The chat's repo's `.centurion/prompts/<kind>.md` replaces it as a whole (`promptFile`: a chat's own folder, an expert's chat's folder; for the default chat folder that is the managing repo's).
- **The CLI** (`docs/cli-plan.md`): `src/cli.ts` is the `centurion` command (start, init, config, api, tools, help); `src/start.ts` runs the manager; `src/init.ts` writes `.centurion/`; `src/docs.ts` renders the self-description from the route table, the config schema and the tool definitions (`managerTools` / `displayTools`), plus `guide/agent.md` for `help --agent`; `src/paths.ts` resolves the package's own files (`prompts/`, `dist/ui`, `guide/`); `src/env.ts` strips a host Claude Code session's variables for agents. Config is found as `.centurion/config.json` in the current folder or a parent (or `--config`); the token is generated into `state/token` next to the state file. `npm run build` compiles `src/` to `dist/server` (the bin) and the UI to `dist/ui`; `prepare` runs it on `npm ci`. Releases: `npm run release -- patch|minor|major|x.y.z` (`npm version` with `preversion` = `scripts/release-check.mjs` (master, clean, equal to origin/master) + typecheck + check:docs, and `postversion` = `scripts/release-push.mjs`, `git push --follow-tags`); pushing a `v<version>` tag runs `.github/workflows/release.yml`, which attaches `centurion.tgz` to the GitHub release (`npm i -g github:...` doesn't work: npm skips the build tools for global git installs).
- `.claude/skills/orchestrate/SKILL.md`: the orchestrator workflow as a skill. Top-level chats get only the short `prompts/orchestrator.md`; this repo is also the managing folder, so its CLAUDE.md and skills load in every chat.
- `README.md`: a short intro, install and usage only; config fields, the API and tools are documented by the CLI (`centurion config`, `api`, `tools`, `help --agent`). Keep it in sync when commands or the install change.

## Design decisions (keep unless the user changes them)

- **One message per turn.** The next queued message is sent only after the previous `result` arrives, so every turn maps to exactly one queue entry.
- **Messaging is async only.** `message_expert` never waits. With `notify` (default on), the parent gets a `[Manager notification]` when the turn ends, and reads the reply with `get_expert_output`. Consecutive notifications are combined into one message.
- **Decisions never mix with chat.** Start (plans) and Send (questions) deliver only the structured choice as one message; Enter in the composer sends only what was typed, and sets the chat's open question sets aside (status `chat`: folded, not waiting, still answerable). A delegation that starts a plan track renders as one line pointing to the round tracker, which owns its status.
- **Images aren't kept.** Claude Code stores sent images in its session file, and history comes from there. The manager only holds images of queued messages, as files in `uploads/<agent>/` next to the state file (the queue entry names them); they are deleted on delivery, on removal from the queue, on stop, and stray ones on startup. The `delivered` event carries the image data once for open transcripts.
- **Handoffs use files.** The orchestrator writes `handoffs/<task>/<expert>.prompt.md` and the expert writes the matching `.findings.md`. Experts get the orchestrator's folder through `additionalDirectories`, unless they have a **task folder** (`task_folder` on `create_expert`, `taskFolder` on a `new_expert` track; optional, anywhere inside the orchestrator's folder, `taskFolder` on the record): then `additionalDirectories` is only that folder and `settings.permissions.blockReads/WritesOutsideWorkingDirectories` make the file tools refuse everything else, in any permission mode. Bash is not confined. The Files panel's second root follows (`rootsOf` in `src/server.ts`).
- **State is one JSON file** (versioned: `STATE_VERSION` and `MIGRATIONS` in `src/state.ts`; a newer file is refused): the registry, queues, session IDs and the last 20 final replies. Writes go through a temp file and a rename, and only the manager writes it. Transcripts are **not** copied; history comes from `getSessionMessages()` (Claude's own session files).
- **Permissions:** `auto` mode with `permissionPrompts: 'host'` and a `canUseTool` callback: what auto can't decide is asked in the UI and **waits indefinitely**; interrupt, stop or the turn ending cancel it. Experts ask the user directly, not through their orchestrator. "Allow for this session" adds rules with destination `session` only, never to settings files. Requests live in memory (`Manager.permissions`). `AskUserQuestion` is denied (use `ask_user`), `ExitPlanMode` allowed. Dev containers will use `bypassPermissions`.
- **Model and effort are per agent and optional.** Unset means `config.model` / Claude Code's default and the model's default effort. Experts created without them take their track's, else their orchestrator's current ones; there is no separate expert default. Changes reach a live process just before its next turn.
- **Fork and rewind work on Claude's session files.** Fork calls `forkSession` cut at the end of the chosen turn into a new agent; rewind forks cut just before the chosen prompt and switches the agent to that session (the old one stays on disk). Files are never rewound. Cut points are prompt uuids: history has them, and `AgentRuntime` sets a `uuid` on every message it delivers. Plans and question sets stay with the chat that made them; waiting ones from rewound turns become `dropped`.
- **Visuals are markup, not code.** Agents describe a visual with elements like `Row`, `Card`, `Tree` and `Code` through `show_visual`; the UI draws it with its own components, so nothing the model writes runs, and the look follows `docs/ui-design.md`. Errors go back to the agent through the tool. The markup lives only in tool calls (not in files, which other programs read); complex diagrams are Mermaid blocks.
- **Subagents are lines, not agents.** Agent / Task calls get their own transcript line with the `task_progress` summary (`agentProgressSummaries: true`); the expanded steps come from the live stream or `getSubagentMessages`. Claude Code's background hand-backs and `<task-notification>` prompts fold into that line.
- **Experts the user starts** (`POST .../experts`) don't notify their chat; the user tells the chat to read their output.
- **Every top-level chat is the same:** it always has the `centurion` tools, and orchestrating is opt-in through the `orchestrate` skill. Internally the kind is still `orchestrator`; the UI calls it a chat.
- **Agents load their own folder's setup:** `settingSources: ['user', 'project', 'local']`, so CLAUDE.md, skills and settings come from the agent's folder and `~/.claude`.
- **Folders are absolute paths**, checked on create. A chat runs in the folder picked when creating it, by default the configured `orchestratorFolder`; it loads that folder's CLAUDE.md and skills, and handoffs land there too. An expert's folder defaults to its orchestrator's folder.
- **Interrupt keeps the queue; stop clears it.** An interrupted turn is recorded as "Interrupted by the user." with `interrupted: true`, not as an error. Chats and experts can be archived, only when not running; a chat takes its experts with it. Archiving closes the process, and a new message unarchives.
- **The file viewer does not edit ordinary files; git actions may write.** Git actions (including stage, discard, switch, merge and conflict resolution) change the index or working tree in the repository of the agent's own folder only. File reads and writable conflict paths must resolve inside an allowed root, links included; raw images are served with a sandboxing CSP. No file watcher: the panel refetches after edit and Bash tool results, at turn end, on window focus and on the `git` event.
- **Git uses the index as the truth.** The staged and unstaged groups reflect it, including work staged by agents. There is no force push. Pull and Sync follow `gitPull` (merge by default) and autostash local changes; switching stashes and restores them when needed. Agents can keep running during git actions and receive no automatic message about them.
- **Keep-warm pings are forks, not turns.** A ping resumes the session with `forkSession: true`, `persistSession: false`, `maxTurns: 1` and the agent's own `buildOptions` (tools stay defined but are denied), so its request has the session's exact prefix and refreshes the cache entry the next turn reads; the session never sees it. Ping texts are numbered so the longest cache match is the session's own entry, not the previous ping's. Pings go out 1 min (5 min TTL) or 5 min (1 h TTL) before the estimated expiry, never while the agent runs or has a queue, and stop at the break-even cap (45 min / 8 h after the last turn), on a miss (< 50 % of the last context read) or a failure, until the next turn.
- **Pausing notifications is a UI toggle per chat.** While `notificationsPaused`, manager messages stay in the queue and others go ahead of them (`isHeld` / `deliverable` in `src/types.ts`, mirrored in `ui/src/status.ts`); keep-warm and the round check ignore held ones. Resuming merges them into one queue entry. No auto-resume.
- **Desktop alerts are per browser** (`localStorage`): defaults for chats (on) and experts (off), and a per-agent override. They go out only while the window is hidden or unfocused, never for the snapshot, and each thing once. Separate from pausing expert notifications.
- **Unread is per browser:** the record has `lastActivityAt`; the UI keeps `lastSeen` in `localStorage`. An open agent only counts as seen while the window is visible and focused.
- **Restarts and idle processes:** after a restart, an agent that was mid-turn becomes `interrupted` and its parent is notified. Idle processes close after `idleMinutes`, and the next message resumes the same session.

## Working here

- **UI work follows `docs/ui-design.md`**: colour only with meaning (state hues, one aqua accent for actions, repo hues on expert marks), the transcript as a document, no coloured left borders, tinted role boxes, cards around everything, gradients, emoji or uppercase labels. Theme values live in `ui/src/styles.css`. When a change alters a rule or pattern there, update the guide in the same commit.
- Backend: TypeScript ESM run with `tsx` in development (`npm start`), compiled to `dist/server` for the installed command. UI: `npm run build` (or `npm run dev` for the Vite dev server with `/api` proxied). Check both with `npm run typecheck`. Line endings are LF (`.gitattributes`).
- Commit each finished part with a short message.
- **Test with a separate config, port and state file** (e.g. in a scratch folder: `npx tsx src/cli.ts --config <file>`, or `centurion init` there and `npx tsx <repo>/src/cli.ts` from it). Real agents use the user's Claude usage, so keep test prompts tiny.
- When you start the manager from inside Claude Code, remove the parent session's env vars (`CLAUDE*`, `ANTHROPIC_BASE_URL`, etc.) or the agents inherit the host session's settings. Use `env -u ...` or `removeEnv`.
- The UI is checked in the browser pane against the test manager (build first, then open `http://127.0.0.1:<port>/?token=...`). Check light and dark and a narrow width. The file `ui/src/timeline.ts` is not named `transcript.ts` because `Transcript.tsx` exists and Windows file names are case-insensitive; likewise `fileStore.ts` next to `Files.tsx`.
- On Windows, stopping a background `npx` leaves `node` running. Stop the process that owns the port.

## SDK gotchas

- `supportedCommands()` works on a prompt-less process too; skills depend on the folder, so the manager caches the list per folder and refreshes it on `commands_changed` events. Builtin commands (`builtin: true`) are hidden in the UI's `/` menu.
- The prompt cache TTL shows in each call's `usage.cache_creation` (`ephemeral_1h_input_tokens` / `ephemeral_5m_input_tokens`); subscriptions use 1 h. The record's `cache` is the start of the last main-loop request plus that TTL, an estimate shown as the header's cache tag.
- `total_cost_usd` in `result` is cumulative per `query()` call; `AgentRuntime` adds up per-turn differences. A resumed process (or a fork of it) also starts from the cost counters Claude Code restored from the session's earlier process, while `result.usage` counts only its own calls: the first turn of a resumed process and every keep-warm ping are priced with `ownCost` (their weighted share of the total).
- `result.usage` adds up every model call of the turn, so it overcounts context after tool calls. Context % uses the last main-loop assistant message's input tokens (plus cache read/write) and `contextWindow` from `modelUsage` (the init message's model).
- `q.interrupt()` ends the turn with its `result` (the process and session stay), and the session writes a `[Request interrupted by user…]` user message into history; the UI shows that as "Interrupted".
- `bypassPermissions` needs `allowDangerouslySkipPermissions: true`, and Claude Code refuses it when running as root.
- A set `ANTHROPIC_API_KEY` takes precedence over the subscription login. Session IDs only exist in the `~/.claude` of the machine that created them.
- Claude Code itself blocks long `sleep` commands.
- Anthropic's cache is keyed per breakpoint: a ping refreshes the entry it reads. Right after a process's first turn, a resumed process reads only the system part (Claude Code's first-turn layout); from the second turn on, resumes and forks hit the whole prefix. A cache write can take a moment before reads hit it.
- `q.setModel()` writes `<command-name>/model…` and `<local-command-stdout>Set model to …` user messages into the session; the UI hides the first and shows the second as an event line. The init message has no effort on SDK processes, so `activeEffort` usually stays null. `supportedModels()` works on a process that has had no prompt yet (no API call), which is how `/api/models` probes when no agent has run.
